1//! The pixel-processing unit draws the screen, and this module is how a program
2//! feeds it.
3//!
4//! The picture comes from six modules: [`tile`] holds the pixels, [`map`] says
5//! which tile goes in which cell, [`bg`] and [`window`] place the two layers
6//! that read a map, [`obj`] carries the sprites drawn over them, and
7//! [`palette`] decides what a pixel's colour index becomes.
8//!
9//! # Reaching video memory
10//!
11//! VRAM and OAM are not always the CPU's to write. The PPU takes them while it
12//! draws, and a write made then is dropped without a word. Every function that
13//! writes takes an [`Access`], which is the answer to "how do you know this will
14//! land".
15//!
16//! [`Direct`](Access::Direct) says the caller is already somewhere it will:
17//! inside a VBlank, or with the LCD switched off. It is the fast answer, and
18//! [`Vblank::with`] and [`with_lcd_off`] are how one is come by. Nothing enforces
19//! the window's length, so a closure that runs past the end of a VBlank loses
20//! the rest of its writes.
21//!
22//! [`Polled`](Access::Polled) says nothing about when it is called, and waits
23//! for the PPU itself instead. It reaches far more of the frame than VBlank
24//! alone, since HBlank recurs on every line, and it blocks until the whole write
25//! is through. For anyone coming from GBDK, this is the shape all of its video
26//! memory writes take.
27//!
28//! ```ignore
29//! let vblank = unsafe { Vblank::listen() };
30//!
31//! // A frame's worth of updates, taken inside the window
32//! vblank.with(|d| {
33//!     map::write(d, bg::map(), col % 32, 0, LEVEL.sub(col, 0, 1, 18));
34//!     obj::set(d, 0, player);
35//! });
36//!
37//! // A bulk load: the screen goes blank, and the window has no deadline
38//! ppu::with_lcd_off(|d| tile::write_all(d, 0, &TILESET));
39//!
40//! // Nowhere in particular: let the write wait for the PPU itself
41//! tile::write(Access::Polled, 5, &spark);
42//! ```
43//!
44//! Work that has to happen between frames belongs before [`Vblank::with`], not
45//! inside it: decide what to draw first, then take the window and spend it on
46//! writes.
47//!
48//! # Writing from a handler
49//!
50//! Much of what follows reads a register, changes a bit and writes it back,
51//! `LCDC` most of all: [`bg`], [`window`], [`obj`] and [`tile`] each own a bit
52//! of it and leave the rest alone. A handler doing the same to the same register
53//! races whatever it interrupted, and one of the two changes is lost.
54//!
55//! [`palette`] fares worse. Its colours travel through an index register, set
56//! once and stepped by the hardware, so a handler writing a palette of its own
57//! sends the rest of the interrupted write into whichever palette it left
58//! selected.
59//!
60//! So a program driving a raster effect from a `STAT` handler should keep its
61//! other writes to those registers in VBlank, where the two cannot overlap.
62//!
63//! # Frame pacing
64//!
65//! A program that uses this module links a weak `_on_vblank` advancing a frame
66//! counter. Writing `#[gb::rt::interrupt(VBlank)]` takes that vector instead,
67//! which nothing reports: such a handler must call [`frame_tick`], or
68//! [`Vblank::wait`] never returns.

99/// How a write reaches video memory.
100///
101/// VRAM at `0x8000` and OAM at `0xFE00` are locked on different schedules: VRAM
102/// is reachable except in mode 3, OAM except in modes 2 and 3, and turning the
103/// LCD off opens both. See
104/// <https://gbdev.io/pandocs/Accessing_VRAM_and_OAM.html>.
105///
106/// Where the hardware has them locked it ignores writes and reads back `0xFF`,
107/// so a value written there is lost rather than wrong, and nothing reports it.
108#[derive(Clone, Copy)]
109pub enum Access<'a> {
110    /// The caller is already inside a window where both are open, so writes go
111    /// straight through.
112    ///
113    /// Minted by [`Vblank::with`] and [`with_lcd_off`], and bounded to the closure
114    /// they run. It is zero-sized and `Copy`, so the lifetime is the only thing
115    /// stopping it being carried out of the window:
116    ///
117    /// ```compile_fail
118    /// # use gb::ppu::{Access, Vblank};
119    /// # let vblank = unsafe { Vblank::listen() };
120    /// let mut saved: Option<Access> = None;
121    /// vblank.with(|d| { saved = Some(d); }); // ERROR: `d` escapes the closure
122    /// ```
123    #[non_exhaustive]
124    Direct(PhantomData<&'a ()>),
125
126    /// Wait for the PPU to release video memory before writing, which makes the
127    /// call safe at any point in the frame.
128    ///
129    /// This reaches far more of the frame than one VBlank does, since HBlank
130    /// recurs on every line. What it costs is the wait, which a bulk write pays
131    /// for every byte: one this way can hold the CPU for more than a frame while
132    /// the picture stays up.
133    Polled,
134}
135
136// A proof about the PPU's current state belongs to the context that read it.
137impl<'a> !Send for Access<'a> {}
138impl<'a> !Sync for Access<'a> {}
139
140impl<'a> Access<'a> {
141    /// Mint [`Direct`](Access::Direct), asserting that video memory is reachable.
142    ///
143    /// The escape hatch for a context [`Vblank::with`] cannot serve, such as a
144    /// VBlank handler, which is already inside the window it would wait for.
145    ///
146    /// # Safety
147    ///
148    /// The PPU must be in mode 0 or 1, or the LCD off. The returned lifetime is
149    /// unconstrained, so the caller must bound it to the period that holds.
150    pub const unsafe fn assume() -> Self {
151        Access::Direct(PhantomData)
152    }
153
154    /// Copy `src` into video memory at `dst`.
155    ///
156    /// # Safety
157    ///
158    /// `dst` must be a VRAM or OAM address with room for all of `src`.
159    pub(crate) unsafe fn write(self, dst: *mut u8, src: &[u8]) {
160        // One routine for VRAM and OAM: `wait_blank` covers the OAM lock as well
161        // as the VRAM one, so there is nothing left to tell the two apart.
162        //
163        // Resolve the discipline once. Monomorphising on it keeps the branch out
164        // of the loop, which matters where a run is only a byte or two long.
165        match self {
166            Access::Polled => unsafe { run::<true>(dst, src) },
167            _ => unsafe { run::<false>(dst, src) },
168        }
169    }
170}
171
172unsafe fn run<const WAIT: bool>(dst: *mut u8, src: &[u8]) {
173    // Walk the destination rather than indexing from `dst`: one fewer value live
174    // across the wait, in a loop the register allocator is already tight on.
175    let mut d = dst;
176    for b in src {
177        if WAIT {
178            wait_blank();
179        }
180        unsafe { core::ptr::write_volatile(d, *b) };
181        d = unsafe { d.add(1) };
182    }
183}

185/// Block until the PPU is between lines or between frames.
186///
187/// Modes 0 and 1 are the two, and seeing either leaves at least 80 dots before
188/// video memory is taken again. Waiting only for mode 3 to pass would not: mode
189/// 2 can be a dot from mode 3, and a write made on the strength of that check
190/// would be dropped after it.
191#[inline(always)]
192pub(crate) fn wait_blank() {
193    use crate::mmio::PpuMode;
194    while matches!(
195        crate::mmio::STAT.read().mode(),
196        PpuMode::OamScan | PpuMode::Drawing
197    ) {}
198}

200/// Advance the frame counter.
201///
202/// Needed only by a VBlank handler that replaced the one this module installs.
203#[inline(always)]
204pub fn frame_tick() {
205    // A read-modify-write, and single-writer: the VBlank handler is the only
206    // caller that matters, and the CPU clears IME on dispatch, so it cannot
207    // interrupt itself.
208    FRAME.set(FRAME.get().wrapping_add(1));
209}

211/// The frame clock: proof that the VBlank interrupt is reaching the counter.
212///
213/// Everything that waits for a frame hangs without it.
214pub struct Vblank(());
215
216// A proof about the hardware's current state belongs to the context that made it.
217impl !Send for Vblank {}
218impl !Sync for Vblank {}
219
220impl Vblank {
221    /// Listen for the VBlank interrupt.
222    ///
223    /// # Safety
224    ///
225    /// Turns interrupts on. That is preemption, which the surrounding code may
226    /// have been written to rule out.
227    #[inline]
228    pub unsafe fn listen() -> Self {
229        // `IE` is read and written back, and another module may have turned
230        // interrupts on already, so the pair is kept off the air.
231        crate::interrupt::disable();
232        unsafe {
233            crate::interrupt::set_enabled(
234                crate::interrupt::enabled() | crate::mmio::Interrupts::VBLANK,
235            );
236            crate::interrupt::enable();
237        }
238        Vblank(())
239    }
240
241    /// Frames counted since boot, wrapping at 256.
242    ///
243    /// [`wrapping_sub`](u8::wrapping_sub) of two readings is the frames between
244    /// them; a plain subtraction is what overflows across the wrap.
245    #[inline(always)]
246    pub fn frame_count(&self) -> u8 {
247        FRAME.get()
248    }
249
250    /// Block until the next frame.
251    ///
252    /// The CPU sleeps while waiting. Does not return with the LCD off, since no
253    /// VBlank arrives then, nor where a replacement handler skips
254    /// [`frame_tick`].
255    pub fn wait(&self) {
256        let seen = FRAME.get();
257        loop {
258            // VBlank is requested at dot 0 of line 144, so LY reading 143 can be
259            // a single dot away from it, and halting there would sleep through
260            // the frame being waited for. Every other line leaves at least 457
261            // dots, against the ~60 this takes to reach the halt.
262            //
263            // LY is read before the counter so a VBlank landing between the two
264            // is caught by the counter read rather than missed. Volatile and
265            // `asm!` accesses keep that order.
266            let near_vblank = crate::mmio::LY.read() == 143;
267            if FRAME.get() != seen {
268                return;
269            }
270            if !near_vblank {
271                crate::interrupt::halt();
272            }
273        }
274    }
275
276    /// Wait for the next frame, then run `f` inside its VBlank.
277    ///
278    /// Nothing enforces the window. `f` keeps running once the PPU has moved on,
279    /// and writes past that point are dropped in silence.
280    ///
281    /// ```ignore
282    /// vblank.with(|d| {
283    ///     bg::set_scroll(d, camera_x, camera_y);
284    ///     obj::set(d, 0, player);
285    /// });
286    ///
287    /// // Overruns: the tail of the tileset lands after the window and is lost.
288    /// // `with_lcd_off` has no deadline.
289    /// vblank.with(|d| load_tileset(&TILES, d));
290    /// ```
291    ///
292    /// Waiting goes through [`wait`](Self::wait), so this does not return under
293    /// the same conditions.
294    pub fn with<R>(&self, f: impl FnOnce(Access<'_>) -> R) -> R {
295        self.wait();
296        f(unsafe { Access::assume() })
297    }
298}

300/// Turn the LCD off for the length of `f`.
301///
302/// The screen goes blank, and in exchange video memory stays reachable for as
303/// long as `f` runs rather than the roughly 1140 M-cycles [`Vblank::with`]
304/// allows, or 2280 in CGB double speed mode. This is how a program loads more
305/// tiles than one VBlank fits.
306///
307/// Unlike [`Vblank::with`], the wait here is a poll and needs no interrupt, so
308/// this runs before a program has turned them on.
309///
310/// [`Vblank::wait`] does not return inside `f`, since no VBlank arrives with the LCD
311/// off. An LCD that was already off is left that way and `f` runs at once.
312///
313/// Turning it back on restarts the PPU at line 0, and the screen stays blank
314/// through that first frame. See <https://gbdev.io/pandocs/LCDC.html>.
315pub fn with_lcd_off<R>(f: impl FnOnce(Access<'_>) -> R) -> R {
316    let lcdc = crate::mmio::LCDC.read();
317
318    // Waiting with the LCD already off would never return, and a caller that
319    // switched it off means to keep it off.
320    if !lcdc.lcd_enable() {
321        return f(unsafe { Access::assume() });
322    }
323
324    // Clearing the enable bit outside VBlank can damage the panel, so wait for
325    // one. The line is polled rather than waited on through `Vblank`: this runs
326    // before interrupts are on, which is where a program loads its tiles,
327    // and it leaves `IME` alone rather than ending a critical section it was
328    // called inside.
329    //
330    // The first loop skips a VBlank already under way, so the second catches the
331    // next one near its start. A handler landing between that read and the write
332    // would have to outlast the rest of the VBlank to push the write out of it.
333    while crate::mmio::LY.read() >= 146 {}
334    while crate::mmio::LY.read() < 145 {}
335
336    // Re-read: a handler may have reconfigured the PPU during the wait.
337    unsafe { crate::mmio::LCDC.write(crate::mmio::LCDC.read().with_lcd_enable(false)) };
338
339    let r = f(unsafe { Access::assume() });
340
341    // Re-read rather than writing `lcdc` back: `f` may have reconfigured the
342    // PPU, and only the enable bit is this function's to restore.
343    unsafe { crate::mmio::LCDC.write(crate::mmio::LCDC.read().with_lcd_enable(true)) };
344    r
345}

347/// Which half of the Game Boy Color's video memory the CPU sees at `0x8000`.
348///
349/// The PPU reads both halves through its own paths, so this is only about CPU
350/// access.
351#[cfg(feature = "cgb")]
352#[cfg_attr(docsrs, doc(cfg(feature = "cgb")))]
353#[derive(Clone, Copy, PartialEq, Eq, Debug)]
354pub enum VramBank {
355    /// Tile slots and the two tilemaps, as on the original Game Boy.
356    Zero = 0,
357    /// A second set of tile slots, and per-cell attributes where bank zero holds
358    /// the tilemaps.
359    One = 1,
360}
361
362/// Run `f` with `bank` mapped at `0x8000`, then put back the one that was there.
363///
364/// The Game Boy Color banks all of `0x8000..0xA000`, so the same
365/// [`tile`] or map write lands in a different place depending on this. Bracketing
366/// it keeps that visible at the call site and out of the surrounding code.
367///
368/// `f` takes nothing: the [`Access`] an enclosing [`Vblank::with`] or
369/// [`with_lcd_off`] handed out is still good here, since which bank is mapped and
370/// whether video memory is reachable are separate questions. The two scopes nest
371/// in either order.
372///
373/// A handler that changes the bank must put it back, the way one that switches
374/// ROM banks must, and one that writes video memory has to set the bank it means
375/// rather than assume zero: it may well have interrupted this.
376///
377/// An original Game Boy has no such register: the write goes nowhere and `f` runs against
378/// the one bank there is, overwriting what was already in it. A cartridge that
379/// runs on both machines has to ask [`is_cgb`](crate::is_cgb) first, there being
380/// no second bank to fall back to.
381///
382/// ```ignore
383/// ppu::with_lcd_off(|d| {
384///     tile::write_all(d, 0, &TILES);
385///     ppu::with_vram_bank(VramBank::One, || tile::write_all(d, 0, &MORE));
386/// });
387/// ```
388#[cfg(feature = "cgb")]
389#[cfg_attr(docsrs, doc(cfg(feature = "cgb")))]
390#[inline]
391pub fn with_vram_bank<R>(bank: VramBank, f: impl FnOnce() -> R) -> R {
392    // Bit 0 is the bank; the rest read as ones.
393    let saved = crate::mmio::cgb::VBK.read() & 1;
394    crate::mmio::cgb::VBK.write(bank as u8);
395    let r = f();
396    crate::mmio::cgb::VBK.write(saved);
397    r
398}
